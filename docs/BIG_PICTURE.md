# The Big Picture: Voidnxsec + Fortress Framework + ADR Ledger

The ultimate goal of this project is to create an **immutable, cryptographically verifiable lifecycle for Linux Operating Systems**. 

Instead of an OS installation being a black box of shell commands that hopefully result in a working system, we are building a system where **every state transition is a mathematical certainty, recorded in an append-only ledger.**

Here is how all the pieces we've discussed fit together into a single, cohesive architecture:

## 1. The Execution Layer: Void Fortress Framework (Shell/C)
At the lowest level, during the actual OS bootstrap (e.g., in a minimal ISO environment or initramfs), we cannot rely on heavy runtimes.
*   **What it is:** The `lib/*.sh` scripts we just created.
*   **Its job:** Execute the raw Linux commands (partitioning, `pacstrap`/`xbps-install`, `chroot`).
*   **The Hack:** Instead of just outputting text, it calculates **deterministic hashes** of the filesystem/state at each phase (e.g., hashing the partition table, hashing the installed base packages) and emits a structured **JSONL Log Event**.

## 2. The Verification Layer: The State Ledger (JSONL / ADR)
This is where the "adr-ledger" synergy comes in. 
*   **What it is:** The continuous stream of JSONL events generated by the Fortress Framework.
*   **Its job:** Act as an **Architecture Decision/State Record Ledger**. Every phase of the installation is an immutable "block" in this ledger.
*   **Why it matters:** If an installation fails, or if a system is compromised later, you have a cryptographic ledger proving *exactly* what state the OS was in at every phase of its creation. You don't just have an error log; you have a verifiable state history.

## 3. The Orchestration Layer: Rust & Go Services
These run on the *host* machine (the machine deploying the OS, or the CI/CD pipeline).
*   **Go Service (`tools/` supercharged):** Parses the JSONL ledger in real-time via gRPC or stdout streams. It provides the high-level API to start, stop, or rollback an installation across a fleet of machines.
*   **Rust Service:** The high-performance verification engine. As the JSONL ledger streams in, the Rust engine recalculates or verifies the cryptographic hashes (`hash` field in our schema) to ensure the target machine's state hasn't deviated from the declarative policy.

## 4. The Declarative Root: Nix Flakes
*   **What it is:** The `flake.nix` we set up.
*   **Its job:** Ensures that the tools used to generate the OS (the shell scripts, the Rust verifier, the Go API) are themselves 100% reproducible. You cannot have a verifiable OS if the tools building it are not strictly versioned.

---

## The Workflow in Action

1.  **Define:** You define the desired OS state (the ADR) in a declarative format.
2.  **Deploy:** The **Go Service** spins up a target environment (VM, bare metal).
3.  **Execute:** The **Void Fortress Framework** (`lib/`) begins executing the phases on the target.
4.  **Record:** At the end of Phase 1 (e.g., "Disk Setup"), the framework hashes the partition state and emits a JSONL event.
5.  **Verify:** The **Rust Service** reads this JSONL event, verifies the hash against the expected state, and appends it to the immutable ledger.
6.  **Progress:** The system proceeds to Phase 2 only because the ledger verified Phase 1.

By merging the ADR ledger concept with the low-level JSONL bootstrap script, we aren't just building an installer; **we are building a verifiable supply chain for the OS runtime environment.**
