# Voidnxsec Roadmap & Pending States

This document outlines the strategic directions, pending integrations, and upcoming major milestones for the Voidnxsec ecosystem.

## 1. ADR Ledger Integration (Highest Priority / Pending Careful Review)

**Status:** Top Priority / Pending Review
**Target:** Orchestration Layer (Rust/Go) & Verification Layer

This is the **first and most critical integration** that requires careful evaluation. The `adr-ledger` project concepts will form the backbone of our cryptographic verification process.

*   **Objective:** Seamlessly map the JSONL state events generated by the `void-fortress-framework` (the execution layer) into a formal, cryptographically verifiable Architecture Decision/State Record (ADR) ledger.
*   **Requirements:** 
    *   Thoroughly review the `adr-ledger` specifications before writing the ingestion logic.
    *   Design the data structures in Rust/Go to ingest the `schema/log-event.json`.
    *   Define exactly how deterministic hashes from the framework are verified against the expected declarative policy.
    *   Ensure the ledger remains append-only and immutable across the entire OS lifecycle.
*   **Next Steps:** Conduct a deep dive evaluation of the `adr-ledger` merge to establish the strict verification interface.

## 2. VoidNxSEC Bootstrap Project with TUI in C (Planned)

**Status:** Planned (Post ADR-Ledger Integration)
**Target:** Execution Layer / User Experience

The C-based TUI is fully planned, but development will be deferred until the core ADR ledger foundation is solidly established.

*   **Objective:** Develop a high-performance Terminal User Interface (TUI) in **C** to serve as the interactive frontend for the VoidNxSEC bootstrap process.
*   **Why C?**
    *   Requires minimal runtime dependencies, making it perfect for custom minimal ISOs (e.g., initramfs).
    *   Provides direct, low-level access to system resources and kernel interfaces (eBPF, netlink) for real-time status updates during the bootstrap phases.
*   **Concept:** The C TUI will act as a fast, secure wrapper around the `lib/*.sh` framework. It will visually represent the phase diagram, parse the JSONL output in real-time, and present the deterministic hashes cleanly to the user.

## 3. GPU Acceleration & CUDA Support (Planned)

**Status:** Planned
**Target:** Execution Layer / Verification Layer

To handle massive parallel verification or complex state calculations, we plan to integrate CUDA support.

*   **Objective:** Leverage NVIDIA GPUs for high-speed cryptographic hashing, complex state analysis, or parallel verification of the ADR ledger.
*   **Implementation Path:**
    *   Introduce C/C++ CUDA bindings within the `/c-app` or `/cpp-app` modules.
    *   Allow the Rust verification engine to offload heavy cryptographic calculations to the GPU during high-throughput verification scenarios.
    *   Ensure graceful fallbacks for systems without NVIDIA hardware.

## 4. Rust & Go Direction Rationale

The division of labor between Rust and Go remains a deliberate architectural choice:
*   **Rust (`rust-service`):** Reserved for the highly secure, deterministic verification engine. It handles cryptographic hash validation, state ledger integrity, and safety-critical orchestration where memory safety and performance are non-negotiable.
*   **Go (`go-service`):** Serves as the high-level API, tooling, and fleet management layer. Its concurrency model and ecosystem are ideal for handling multiple deployment streams, serving REST/gRPC endpoints, and interacting with CI/CD pipelines.
